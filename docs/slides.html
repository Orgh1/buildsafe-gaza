BuildSafe Gaza

Building Damage Assessment Platform — an offline-capable web app for field engineers assessing damaged buildings in Gaza (2023).

Team: Mahmoud Irheem · Osama Al-Ghazali · Yasser Awda · Ahmed El-Naggar · Kerim Ebu Musameh

The Problem

After the 2023 destruction, thousands of buildings in Gaza need evaluation. Today, assessments are:

  • 📝 Done manually on paper — slow and error-prone
  • 🔀 Not standardized — every engineer documents differently
  • 📤 Hard to document & share — no central record
  • 📶 Difficult in areas with limited / unstable internet

There is no unified, digital system for building damage assessment.

Our Solution

A digital platform that lets field engineers:

  • Enter building & owner data and classify damage type + severity
  • Attach photos and videos as evidence
  • Generate a structured PDF report in one click
  • Work offline and sync automatically when back online

Faster · standardized · reliable — even with no connectivity.

System Architecture — Three Tiers

① Presentation Layer — PWA
HTML5 · CSS3 · Bootstrap 5 · JavaScript · Service Worker (app-shell cache) · IndexedDB (offline store)
▼   HTTPS · JSON / multipart
② Application Layer — Node.js + Express REST API
Auth (JWT + bcrypt) · Assessments · Media · Sync · PDF reports (PDFKit) · Stats
▼   better-sqlite3
③ Data Layer
SQLite relational DB (engineers · assessments · media · contacts · activity_log) + file storage for media

Separation of concerns → maintainable, scalable, secure. (See diagrams.html for full UML.)

  • assessments — id, client_uuid (offline dedup key), engineer_id, owner & building fields, damage_type, severity, habitability, status, source
  • media — id, assessment_id, filename, mime_type, kind (image/video), size
  • contacts, activity_log — feedback & engineer activity tracking

The Highlight — Offline-First

The hardest, most valuable requirement: keep working with no internet.

1 · Engineer fills form (offline)→ 2 · Saved to IndexedDB with client_uuid→ 3 · Navbar shows “N pending”
4 · Connection returns → online event→ 5 · POST /api/sync (records + base64 media)→ 6 · Server upserts by client_uuid→ 7 · Synced records cleared locally

Idempotent sync = no duplicates, even if sync runs twice.

The Service Worker precaches the whole app shell, so the app itself loads with zero network.

Security & Reliability

  • 🔐 Passwords hashed with bcrypt; sessions via JWT in an httpOnly cookie
  • 🙅 Ownership isolation — engineers can only read/edit their own assessments & media
  • ✅ Server-side validation on every write (required fields, enums, ranges)
  • 🛡️ Security headers (nosniff, X-Frame-Options), upload type/size limits
  • 💾 Reliable storage in a relational DB; idempotent sync prevents data loss/duplication
