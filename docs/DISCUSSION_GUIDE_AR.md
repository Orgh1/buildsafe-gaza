# دليل المناقشة الشامل — BuildSafe Gaza (منصة تقييم أضرار المباني)

> ملف دراسة لكل الفريق قبل المناقشة. مقسّم على الأجزاء، وكل عضو يركّز على قسمه لكن يفهم الكل.

---

## 0. الجملة الافتتاحية (يحفظها من يبدأ العرض)
«BuildSafe Gaza منصّة ويب تساعد المهندسين الميدانيين على تقييم المباني المتضررة جزئياً في غزة،
بإدخال بيانات المبنى والمالك، توثيق الضرر بالصور، وتوليد تقارير منظّمة — **وتعمل حتى دون إنترنت**
ثم تُزامن البيانات تلقائياً عند عودة الاتصال.»

---

## 1. الفكرة والمشكلة (نظرة عامة)
- **المشكلة:** بعد دمار 2023، آلاف المباني تحتاج تقييماً. التقييم اليوم **يدوي، غير موحّد، صعب التوثيق والمشاركة**، وصعب في مناطق ضعيفة الإنترنت.
- **الحل:** نظام رقمي موحّد: نموذج فحص واحد لكل المهندسين + صور + تقرير تلقائي + عمل دون اتصال.
- **المستخدمون:** (1) المهندس الميداني، (2) المنظمات الإنسانية، (3) الجهات الحكومية.
- **الأثر:** تقييم أسرع، بيانات دقيقة موحّدة، واستمرار العمل رغم ضعف الشبكة.

---

## 2. المتطلبات (Requirements)

### 2.1 وظيفية (Functional) — ماذا يفعل النظام
1. **مصادقة المهندس:** تسجيل دخول آمن + إدارة جلسة.
2. **الملف الشخصي:** عرض/تعديل البيانات وتغيير كلمة المرور.
3. **سجل التقييمات:** عرض التقييمات السابقة وتتبّع حالتها.
4. **تتبّع النشاط:** تسجيل أفعال المهندس (جدول `activity_log`).
5. **إدارة التقييمات:** إنشاء/تعديل/حذف/عرض (CRUD).
6. **توثيق الضرر:** نوع الضرر + الشدّة + قابلية السكن + ملاحظات.
7. **إدارة الوسائط:** رفع صور/فيديو وربطها بالتقييم.
8. **توليد التقارير:** تقرير منظّم قابل للطباعة/الحفظ PDF.
9. **دعم العمل دون اتصال + المزامنة.**
10. **التواصل:** نموذج تواصل/ملاحظات.

### 2.2 غير وظيفية (Non-Functional) — كيف يؤدّي النظام
- **قابلية الاستخدام** (واجهة بسيطة)، **الاستجابة** (Bootstrap يعمل على الجوال والحاسوب)،
  **الأداء** (تحميل سريع)، **الأمان** (bcrypt + JWT + تحقّق)، **الموثوقية** (قاعدة بيانات + مزامنة بلا تكرار)،
  **قابلية الصيانة** (فصل الطبقات)، **قابلية التوسّع**، **التوفّر دون اتصال**.

---

## 3. المعمارية — ثلاثية الطبقات (Three-Tier)
```
① طبقة العرض (Presentation) — المتصفح/الجوال (PWA)
     HTML5 · CSS3 · Bootstrap 5 · JavaScript
     + Service Worker (تخزين التطبيق) + IndexedDB (تخزين أوفلاين)
                    │  HTTPS (JSON + رفع ملفات)
② طبقة التطبيق (Application) — Node.js + Express (REST API)
     المصادقة · التقييمات · الوسائط · التقارير · المزامنة · الإحصائيات
                    │  better-sqlite3
③ طبقة البيانات (Data) — قاعدة SQLite + مجلد ملفات للوسائط
     engineers · assessments · media · contacts · activity_log
```
**لماذا ثلاث طبقات؟** فصل الاهتمامات → صيانة أسهل، أمان أعلى، وإمكان تغيير أي طبقة دون الأخرى.
**تدفق الطلب:** المستخدم → الواجهة → الـ API → قاعدة البيانات → الرد يعود للمستخدم.

---

## 4. قاعدة البيانات (Database)
- **النوع:** SQLite (علائقية) — ملف واحد `data/buildsafe.db` يُنشأ تلقائياً؛ المخطط في `src/db/schema.sql`.
- **الجداول والعلاقات:**
  - `engineers` (1) ──< `assessments` (متعدد) ──< `media` (متعدد)
  - `engineers` (1) ──< `activity_log` (متعدد)
  - `contacts` (مستقل)
- **حقول مهمة في `assessments`:** `client_uuid` (مفتاح لمنع تكرار المزامنة)، `severity`، `status`، `source` (online/offline-sync).
- **لماذا SQLite؟** قاعدة علائقية حقيقية (SQL، مفاتيح أجنبية، معاملات) وسهلة التشغيل والعرض دون خادم منفصل. نفس المعمارية والنموذج ينطبقان لو انتقلنا لـ SQL Server/PostgreSQL لاحقاً (نغيّر طبقة البيانات فقط).

## 5. التقنيات وتبريرها (Tech Stack)
| الطبقة | التقنية |
|---|---|
| الواجهة | HTML5, CSS3, Bootstrap 5, JavaScript, PWA (Service Worker + IndexedDB) |
| الخادم | Node.js + Express, JWT, bcrypt, Multer (رفع)، PDFKit |
| البيانات | SQLite (better-sqlite3) + تخزين ملفات |
| الأدوات | Git/GitHub, Jira, Google Drive, Render (نشر) |

> **سؤال متوقّع:** «التقرير يقول ASP.NET Core + SQL Server، ليش Node + SQLite؟»
> **الجواب:** المقرر يسمح بأي إطار مناسب، والمعمارية ثلاثية الطبقات ونموذج البيانات لم يتغيّرا؛ SQLite قاعدة علائقية حقيقية وأسهل للتشغيل والعرض، والترقية لقاعدة أكبر تمسّ طبقة البيانات فقط.

## 6. شرح الميزات تقنياً (كيف تعمل فعلاً)

### 6.1 المصادقة (Ahmed)
- التسجيل: كلمة المرور تُشفَّر بـ **bcrypt** (لا تُخزَّن كنص). أول مستخدم يصبح admin.
- الدخول: يتحقق من الكلمة، ثم يُصدر **JWT** يُخزَّن في **httpOnly cookie** (لا يصله جافاسكربت → حماية من XSS).
- الوسيط `requireAuth` يتحقق من التوكن في كل طلب محمي؛ و`requireAdmin` للمدير فقط.
- **العزل:** كل مهندس يصل لتقييماته فقط (اختبار TC9).

### 6.2 التقييمات والوسائط (Osama)
- CRUD عبر `routes/assessments.js` + `services/assessments.js`؛ تحقّق من المدخلات في `utils/validate.js` (حقول مطلوبة، قيم enum، نطاقات أرقام).
- الوسائط: `Multer` يستقبل الملفات، تُحفَظ في `data/uploads/` وبياناتها في جدول `media`، وتُخدَّم عبر `/api/media/:id` مع تحقّق الملكية.

### 6.3 التقارير ولوحة التحكم (Mahmoud)
- التقرير يُبنى في **المتصفح** (صفحة `report.html`) ليعرض العربية وRTL بشكل صحيح، ويعرض فقط الحقول المعبّأة، وزر «طباعة/حفظ PDF».
- لوحة التحكم: `/api/stats` يُرجع إجماليات وتوزيع الشدّة وأحدث التقييمات.

### 6.4 الأوفلاين والمزامنة والتعريب (Kerim) — أهم ميزة
1. **العمل دون اتصال:** النموذج يكتشف `navigator.onLine=false` فيحفظ التقييم (والصور base64) في **IndexedDB** بمعرّف `client_uuid`.
2. **المؤشّر:** شريط التنقل يُظهر «غير متصل» و«N بانتظار المزامنة».
3. **المزامنة:** عند عودة الاتصال (`online`) يرسل السجلات إلى `/api/sync`.
4. **بلا تكرار (Idempotent):** الخادم يعمل **upsert على `client_uuid`** → لا تتكرر البيانات حتى لو تكررت المزامنة (اختبار TC6).
5. **Service Worker** يخزّن التطبيق (network-first) فيعمل دون شبكة، ويخزّن الصور للعرض أوفلاين.
6. **التعريب:** ملف `i18n.js` يترجم كل النصوص ويقلب الاتجاه RTL، والأرقام تبقى إنجليزية.
7. **PWA:** manifest + أيقونات → قابل للتثبيت على الجوال.

## 9. الأمان (Security)
- كلمات المرور: **bcrypt** (تجزئة).
- الجلسة: **JWT في httpOnly cookie**.
- **تحقّق من المدخلات على الخادم** لكل عملية كتابة.
- **عزل الملكية** (كل مهندس لبياناته)، ورؤوس أمان (nosniff، X-Frame-Options)، وحدود لنوع/حجم الملفات المرفوعة.
